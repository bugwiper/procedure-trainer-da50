## Decisions (assumptions taken in planning; the owner may veto any of them)

Owner decisions R-15 to R-26 of the section "Rework decisions R-15.." in `07-CONTEXT.md` apply; read that section first, it holds the exact catalog entries, the geometry numbers and the wording rules. Plans 07-04 and 07-05 and the two part-A commits (4fb82ac, ca516a2) are done: no mode, a slim run view of the pad, the footwell cluster with the preselected conduct, SHOW CHECKLIST on every level.

- **S-01 (R-16) Catalog model.** `src/engine/catalog.ts` (pure, no scenario fact): `CatalogEntry { tag, detail?, ref? }` with `ref` `{ pack, scenario }`, `CatalogGroup { id, heading, tab, entries }`, `defineCatalog({ groups })` returning a frozen `CatalogSet` with `groups`, `entryKey(groupId, entry)` (group id plus a slug of tag and detail, unique in the catalog), `groupOf(ref)`, `entryOf(ref)` and `order(items)` (stable catalog order for any items that carry `pack` and `scenario`, unknown ones after the entries of the last group in their given order). `defineCatalog` throws a `CatalogError` for an empty tag, a repeated group id, a repeated entry key or a `ref` used twice. `AircraftEnv` gets the field `catalog` and `DA50RG_ENV` the value from `src/aircraft/da50rg/checklist-catalog.ts` (export `DA50RG_CATALOG`; the scenario ids appear only there, in `src/aircraft`).
- **S-02 (R-16) Cross-check.** `src/scenario/catalog-check.ts` exports `checkCatalog(env, shipped)` for `shipped` as a list of `{ pack, id, heading }` read from the validated packs; `validateAll` calls it once after the packs. L29: every shipped scenario is the `ref` of an entry and every `ref` names a manifest entry of a pack; L30: the tag of a linked entry equals the `checklist.heading` of its scenario (the scenario title when the file has no heading). Issues are reported on the catalog file (line 1, column 1) or on the scenario file. No per-open lint, no throw at run time.
- **S-03 (R-18) Session.** `listChoices` returns the allowed choices ordered by `env.catalog.order`; new signal `chooseGroup` (a group id, default the first group that has a choice) and method `chooseTab(id)` (resets `choosePage`, ignored outside `choosing` and while busy); `nextPage` wraps inside the selected group; the frame filters `choices` by `env.catalog.groupOf`. `closeChooser`, `toFreePanel` and every start reset the group. `pageCount` and `pageSlice` keep their signatures and read `maxRows`.
- **S-04 (R-18) Pad rectangles.** `SESSION_LAYOUT.choose` gets `tabs` (three 116.67 wide rectangles with 10 unit gaps over x 35 to 405, y 110, 80 high), `rows` become 3 at y 200, 290, 380 and `maxRows` 3; `sessionFootprints` includes the tabs. The tab labels are the `tab` field of the catalog groups (static, G-0), the aria labels the full headings. The independent typed rectangles are updated in `tests/zoom.test.ts`, `tests/layout.test.ts` and `tests/session-run-view.test.ts`; a case asserts that the number of tab rectangles equals the number of catalog groups of the independent reference.
- **S-05 (R-17) Sheet list.** `RunChecklist` renders `role="tablist"` tabs with the full headings (test ids `run-checklist-tab-<group id>`), the entries of the selected tab in catalog order (`run-checklist-entry` for a loaded scenario, `run-checklist-entry-greyed` with `disabled` and `aria-disabled` otherwise, the detail as a second span). The loaded entries still come from `loadChecklistList` (all allowed scenarios, once per run); a catalog entry is a button when its `ref` is among the loaded entries. New signal `checklistTab` (first group at every run start, kept until the run ends).
- **S-06 (R-23, R-24) Outline contract.** `buildOutline(scenario, branches, mode, result?, manual?)` with `manual = { keys, autoSteps }`: `keys` is the set of ticked row keys of the shown checklist, `autoSteps` is `all` (own checklist with marks: every step is program-checked), `panel` (foreign checklist with marks: a step is program-checked when `panelOnly(step.done)`) or `none` (no marks: no step is program-checked). In the live mode `OutlineLine` and `OutlineStep` get an optional `tap { key, on }`: present on every `line` row, and on a `step` row that is not program-checked; `on` is the tick. A step that is program-checked keeps `verdict Done` from the grade and never gets `tap`. The live mode accepts no `result` when `autoSteps` is `none`. Row keys are `line:<path>` and `step:<id>`. `ChecklistOutline` renders a tap row as a `button` (`aria-pressed`, `data-testid="sheet-tap"`, `data-ticked`, minimum height 44 px, the existing green tint of a Done row for a ticked one, no text change).
- **S-07 (R-24) Marks from the real actions.** `src/engine/predicates.ts` exports `panelOnly(predicate)`: true for the checks `state`, `state_in`, `travel`, `travel_rel`, false for `quantity` and `band`. In `session.ts` the shown checklist is the opened scenario (own) or the loaded entry of the choice (foreign). `computeMarks` grades the real recording against the own file, or the foreign recording (the real events, the scenario id of the chosen file, no variant, no decisions, the onset only when the chosen file declares an onset section) against the chosen file, in a try block: a throw gives no marks. Cache: one entry keyed by the ref of the shown checklist and a key of the user log (its length and the identity of its newest event). The existing synchronous-then-trailing coalescing (`slowMarks`, `TRAILING_MARKS_MS`) stays. Marks stay `null` before the onset, while the sheet is hidden and while the list is shown.
- **S-08 (R-23) Ticks.** Session signal `manualMarks` (a set of composite keys `<pack>/<scenario>|<row key>`), method `toggleManualMark(rowKey)` (running only, composes the key with the ref of the shown checklist, a second call clears it), and a computed set for the shown checklist. Cleared by `clearRunHelp` (start, complete, leave) and by `closeDebrief`, Retry and Next; a unit case per exit. The recording and the grade never read it (a case compares the JSON of the recording and of the grade with and without ticks).
- **S-09 (R-24) Debrief checklist line.** `checklistNote(choice, ownRef, title)` in `src/ui/debrief-text.ts` returns the neutral line or null (Realistic with a choice that is not the own checklist); `Debrief` gets the prop `checklistNote` after `checklistUsed` and prints it as `debrief-checklist-note` under the "Checklist used" line.
- **S-10 (R-15, R-21, R-22) Further data.** `FurtherOption` gets `avoid?: true`; `FurtherDefinition` gets `noteConduct` (names a conduct option; `defineFurther` checks that it is one and that every `avoid` option is an unrated action). Aircraft list order after the change: atc_mayday, atc_pan_pan, brief_passengers, avoid_imc, avoid_nvfr, avoid_icing, then the three conducts (the conduct id `conduct_destination` replaces the old one, label two lines). `Further` schema gets `conduct_note: wordsBetween(1, 50).optional()`; lint L31 rejects it unless `accept` lists the `noteConduct` option. `conductNote(result, section, set)` in `debrief-text.ts` returns `{ tone: 'standard' | 'done', lines }` or null as R-22 says; the labels in the lines are the `text` of the Avoid options. `FurtherAreaFrame` leaves out the conduct options and the `avoid` options when the scenario offers no conduct (the existing `offersConduct`).
- **S-11 (R-21) Geometry.** Start with the numbers of R-21, measure on the real profiles with the harness of `tests/zoom.test.ts` (both landscape phones at their real run heights, three portrait phones, desktop and tablet), edit `further-pad.ts`, `plates.ts`, `panel.ts` and the independent tables (`tests/further-pad-reference.ts`, the typed rectangles of `tests/layout.test.ts` and `tests/zoom.test.ts`) together, in one commit. The stop rule of R-21 applies.
- **S-12 (R-19) CAS.** Only the two message texts and the prose that names them change; rule ids, quantity ids, timers and the switch plate text stay.
