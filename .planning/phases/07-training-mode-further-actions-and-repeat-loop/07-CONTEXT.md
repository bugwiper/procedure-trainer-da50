<domain>
## Phase Boundary

The learning loop. A pilot can run a situation in Training mode (checklist on demand, hints), make the non-panel decisions of the situation (inform ATC, brief passengers, further flight conduct) that are graded with the panel actions, retry the same situation or move to the next one from the debrief, and a developer can add a scenario by following the README. Out of scope: the emergency-landing follow-on scenario and landing scene (todo, D-12), any new panel physics, new scenario packs, tooling for non-developers.

</domain>

### Scope and order

### Training mode (SES-02)
- **D-02 (owner):** Training/Exam is its own axis, independent of the level (Easy, Medium, Realistic), chosen on its own card like the level. It is display state of the session (`session.mode`, `session.modePicked`), never an input of `grade` (like the level, GRADING.md "What goes in"). Default value `exam` (the behaviour before Phase 7), so the unit paths that never pick a mode are unchanged. The debrief names it ("Mode: Training|Exam"). Card order is mode, then level, then briefing or run (planner: mode first because Realistic starts the run at the level pick; owner may veto).
- **D-03 (owner):** Training: the scenario checklist can be shown or hidden during the run (the `ChecklistOutline` in its briefing form, in a non-modal sheet: the run clock keeps running and the panel stays operable; available on every level, also Medium and Realistic) and a Hint button. Exam: silent, none of that (no buttons are drawn and the session methods do nothing).
- **D-04 (owner):** A hint names the next open checklist step in the printed wording (row mark, text, action), derived from scenario data, no new text per scenario. Rule (planner): `grade` on the current partial recording (pure), the first graded step in declared order with severity critical or standard that is not credited; optional steps are never named; with none open one fixed sentence. A hint never touches grading, a hint count is not kept. On Realistic nothing is given before the onset (the hint would give the failure away).
- **D-05 (planner, owner may veto):** While a run is live the session area (region `scenario_area`) shows a run view: FURTHER ACTIONS (07-02), CHECKLIST and HINT side by side (Training only), NEW SITUATION and CHOOSE SITUATION side by side, RESET. The ids `session.new`, `session.choose`, `session.reset` and their leave-run confirm stay, only the rectangles change (`SESSION_LAYOUT.run`, with an independent hand-written reference). Labels are static (G-0); the shown checklist is marked by the pressed rim, not by text. The hint line is a non-modal strip that takes no press (`pointer-events: none`). Fallback if the owner dislikes the pad: the same buttons in the footer next to Procedure complete.

### Further actions (SES-05)
- **D-06 (owner):** A fixed global list in aircraft data (`src/aircraft/da50rg/further.ts`, read through `AircraftEnv.further`; the UI and lint read it, no id or text is hard-coded elsewhere). (1) Inform ATC, then the second selection: MAYDAY (121.5 or current frequency) or PAN PAN PAN (advise ATC); (2) Brief passengers (if time permits); (3) Choose further flight conduct: Continue flight normally, Initiate precautionary (alternate) landing, Initiate emergency landing. Removed: set squawk, secure cabin, monitor oil, position report, repeat checklist. Option ids: `atc_mayday`, `atc_pan_pan`, `brief_passengers`, `conduct_continue`, `conduct_precautionary`, `conduct_emergency`.
- **D-07 (owner, 2026-11-01):** Multi-select. Any combination of further actions in one run; the modal and the recording allow it. Every pick is one logged decision `{ t, id }` (run clock time, order chosen) in the recording field `decisions`, beside the store log (which stays for controls). An action picked twice is logged once. The conduct may be picked again (escalation); the last conduct pick counts, earlier picks are shown in the debrief. No retract. The modal pauses the run clock like every modal. A pick before the Realistic onset is ignored.
- **D-08 (owner):** Per option a scenario declares a role: `required`, `recommended`, `optional` or `harmful` (an option not listed is `optional`). Required and missing: fails like a missed critical step. Recommended: shown in the debrief, never changes the verdict. Harmful: shown, fails the run only with `fails_run: true` (as the forbidden items). Brief passengers is never `required` and never fails: `optional` (informative) in alternate-landing situations, `recommended` in emergency-landing situations. The model has no "either call" role; where a printed page says only "inform ATC" both calls stay `optional` (open point for the owner, D-13).
- **D-09 (owner, 2026-11-01):** The flight conduct is declared explicitly: `conduct: none` or `conduct` with `accept` (the correct option ids). With `accept` it is required: no pick, or a last pick outside `accept`, FAILS the run (reason `conduct`, status missing or wrong). With `none` no conduct decision exists in that scenario: the modal does not offer it and its absence never fails. Lint: a scenario on the ground (the aircraft's ground parameter, `env.further.groundParameter`, above 0 in the profile; ground scenarios) must declare `none`; any other scenario that has a `further` section must declare `accept`; `accept` must not list every option.
- **D-10:** Format 1 stays valid: `further` is an optional section. A scenario without it grades no further action, the modal offers ATC and passengers unrated and no conduct, and its grade result is JSON-identical to before (the result key is absent). A recording without `decisions` means none made. Every shipped scenario declares `further` (a unit test, not a lint rule). The do-nothing rule L11 stays; the L20 solution run of variants now also makes the required decisions.
- **D-11:** Verdict reasons, in this order: outcome, critical_missed, further_missed (count of required options not picked), conduct, order, forbidden, further_harmful. Decisions after an outcome time are not graded (like events). Rules R16 to R19 go into `docs/GRADING.md` (07-02).
- **D-12 (owner):** The emergency-landing follow-on scenario (with or without engine power, landing scene, newly printed checklist) is not in this phase. The choice is recorded and graded; when the last conduct pick is the emergency landing the debrief shows one note (text in aircraft data) that the landing itself is not trained yet; the todo `2026-10-28-emergency-landing-scenarios.md` gets the status.
- **D-13 (planner defaults, owner corrects; listed in `docs/PANEL-REVIEW.md` "Phase 7: owner review", 07-03):** Roles fail only where the printed page or an owner decision requires it; conduct is safety-conservative.

### Retry and next (SES-06)
- **D-14 (owner left open, planner decision, owner may veto):** Retry (debrief) starts the same scenario from a clean initial state (panel at the scenario baseline, quantities reset, new clock, empty log and decisions) at the same level and mode, with the same variant (cause) and, on Realistic, the same onset time, so a better result comes from the pilot, not from the draw. The seeds come from the graded recording; one function decides it, so a "new seed" rule is a one-line change. Next situation (debrief) opens the next scenario in listing order (all allowed packs, manifest order, wrapping), keeps mode and level (Realistic only if the next scenario declares an onset, else the level card is shown) and goes to its briefing (Easy, Medium) or starts it (Realistic). NEW SITUATION stays the random pick. Both buttons are ignored while a load runs.

### 07-04: the learning part

- **R-01 (owner) No mode.** The Training/Exam card and the whole mode concept are removed: the user picks only Easy, Medium or Realistic (the level card is the first card after a scenario is opened; Retry and Next situation keep the level only). Removal list for code, tests, e2e and docs: `Mode`, `MODES`, `MODE_NAMES`, `MODE_HINTS`, `TRAINING_NOTE`, the signals `mode` and `modePicked`, `setMode` and the mode handling in `openBriefing`, `nextSituation` and `retry` (session.ts); `src/ui/screens/ModePick.tsx`; the `mode` props of `Briefing` and `Debrief`, the Training note (`briefing-training`) and the Debrief line `debrief-mode`; the mounting and `setMode` in `App.tsx`; the e2e helper `pickMode`, the `mode` parameters of `chooseScenario`, `startScenario`, `startRealistic` and the test id `mode-pick`; the mode sentences in `README.md`, `docs/GRADING.md` and the "Training only" notes in `docs/PANEL-LABELS.md`. The Exam sentence of the briefing becomes a mode-free note, test id `briefing-note`: "When you are done, press Procedure complete." SES-02 and SES-03 are reworded in 07-05 (R-12).
- **R-02 (owner) CHECKLIST on Easy and Medium.** The button is drawn in every run on Easy and Medium (a real pilot always uses the checklist); the label CHECKLIST is static, the shown sheet is marked by the pressed rim (G-0). The sheet is the non-modal sheet of H-04 and shows the scenario's own checklist in the briefing form. Steps already done are marked GREEN, as the debrief outline does, from the credit of the graded steps (`grade` of the partial recording, `result.steps[].credited`; no new rule, rule R12 applies): a new outline mode `live` in `src/ui/outline.ts` (`buildOutline(scenario, branches, 'live', result)`) prints the briefing form and gives a credited step the verdict "Done" in tone `done`; a step not done carries no tag and no verdict (never "Missed"). The sheet updates live, once per logged panel event or retract while it is shown (no work per tick, no work while it is hidden; if one `grade` call on a 30-minute log costs more than about 30 ms the refresh is coalesced). On Realistic nothing is marked before the onset.
- **R-03 (owner) CHOOSE CHECKLIST on Realistic.** On Realistic the same button reads CHOOSE CHECKLIST (static label, chosen at the run start). It opens the same sheet at a list of the checklist headings of all scenarios of all allowed packs (`checklistHead(...).heading`, else the scenario title), in listing order, with no hint which one belongs to the situation. The list loads the scenarios lazily through the pack seam on the first press (allowed packs only, no `loadFailure` modal: a failure shows a message and Try again inside the sheet, the run goes on). Choosing an entry shows that checklist in the briefing form (branches as for that scenario's own start state); the sheet has a button to go back to the list, multiple switches are allowed. Done steps are marked green only when the chosen checklist is the scenario's own (same `ScenarioRef` as the opened scenario); for any other checklist nothing is marked. The last choice is kept as display state of the run (signal, like level; the `Recording` is unchanged) and named in the debrief: "Checklist used: <heading>" on Realistic only, "Checklist used: none" if nothing was chosen. It does NOT affect PASS or FAIL: `grade` receives neither level nor choice (a unit test compares the JSON of one recording with and without choices). A new run (start, Retry, Next, leave) clears the choice. The sheet may be opened before the onset (it shows all checklists alike and so names nothing).
- **R-04 (owner) HINT on Realistic only.** Easy and Medium have no hint. On Realistic the HINT button toggles an expandable box (non-modal, over the windscreen like the old hint line, takes no press) that shows the situation name (`scenario.title`, for example ALTN 1 FAIL) and the situation text of the Medium briefing (`scenario.briefing.situation`, the file's own scenario, so the cause of a variant stays hidden); a second press hides it (the box must disappear; the button shows the pressed rim while the box is shown). Withheld before the Realistic onset (the press does nothing). Cleared when the run ends. It gives no step-by-step guidance.
- **R-05 (owner) The old hint engine goes.** Removed with its tests: `src/engine/hint.ts` (`nextOpenStep`, `openFurtherItems`, `OpenStep`, `OpenFurther`), `tests/hint.test.ts`, `src/ui/screens/HintLine.tsx` (replaced by `HintBox.tsx`), the session members `hint`, `HintState`, `askHint`, `HINT_NONE_TEXT`, `HINT_FURTHER_TEXTS`, `hintNoneText`, and the hint-line CSS (replaced by the box CSS). The green marking uses `grade` directly and does not need any part of `hint.ts`. The review items IN-02 and IN-03 are obsolete with it.
- **R-06 (owner, rectangles planner) The pad in a run and outside.** During a run the pad shows only what the run needs: CHECKLIST (Easy, Medium) or CHOOSE CHECKLIST plus HINT (Realistic), and a small LEAVE. LEAVE (id `session.leave`, label LEAVE) is the old way out: it calls `resetPanel()`, so the existing leave-run confirm asks first and leaves to the free panel. NEW SITUATION, CHOOSE SITUATION and RESET are drawn on the free panel only; their confirm kinds stay in the session (unit-tested) but no button reaches them during a run. Outside a run the main view is as before but narrower: the three buttons 280 wide (x 80) instead of 370, same heights (hit targets stay at least 44 px on screen on every device profile). Starting values (region-local, region 440 x 480; the executor adjusts after the screenshot review and edits data and independent references together): run view `checklist` x 35, y 20, 370 x 80; `hint` x 35, y 116, 370 x 80; `leave` x 228, y 404, 177 x 64; in 07-04 only a temporary `further` (x 35, y 212, 370 x 80) keeps the old FURTHER ACTIONS button and modal alive until 07-05 deletes both. The choose view is unchanged. The pad stays in the co-pilot legroom.

### 07-05: the further actions as toggles

- **R-07 (owner) A cluster of six toggle buttons in the pilot footwell.** The optional further actions are drawn all at once, no modal: BRIEF PASSENGERS, MAYDAY, PAN PAN PAN (top row) and CONTINUE NORMALLY, ALTERNATE LANDING, EMERGENCY LANDING (bottom row). The place is a new trainer region `further_area` with a plate `further-pad` between the under-panel row and the toe brakes (pilot footwell, a named exception of the legroom gate like `pedals`). Starting values (global): plate x 200, y 880, 640 x 230, rx 12; region x 220, y 900, 600 x 190 (20 units of plate on every side); slots region-local, three columns x 0, 205, 410 (190 wide), rows y 0 and 103 (87 high). Free space checked against the data: the under-panel pulls end at y 865, the pedals plate starts at y 1130, the cabin plate ends at x 116, the legroom is x 20 to 930 and y 760 to 1290. Slots and short labels are aircraft data (`src/aircraft/da50rg/further-pad.ts`, the labels as a `label` field of each option in `further.ts`, the long `text` stays for the debrief), with an independent hand-written reference (`tests/further-pad-reference.ts`) and an updated reference for the legroom gate, the region lists and the Full panel footprints. The plate is static shell art and stays on the free panel; the buttons are drawn during a run only (owner may veto: an empty plate on the free panel).
- **R-08 (owner; representation planner) Toggle semantics and recording.** Each button is a toggle shown highlighted when selected; selection shows by highlight only (tint of the face plus the pressed rim and `aria-pressed`, G-0). MAYDAY and PAN PAN PAN are independent toggles (either, both or none); BRIEF PASSENGERS is a toggle; the three conduct buttons are a radio group (pressing another switches, pressing the selected one clears it). Representation: the existing `decisions` model gets an optional `on` flag, `RecordedDecision { t, id, on? }`, absent meaning on, so every recording and golden fixture made before stays valid and grades byte-identically. A press appends one entry (an action: `on` is the opposite of its state now; a conduct: on for another option, off for the selected one). **The last state counts:** an action is done when its last entry is on; the conduct is replayed in order (an on entry selects, an off entry clears when it names the selected option); `picks` in the result stays the history of the on entries (shown in the debrief), `last` becomes the selection at the end (null when cleared; status then `missing` for `accept` as before). One pure helper `effectiveSelection(decisions, set)` in `src/engine/further.ts` gives `{ actions, conduct }` to `gradeFurther`, the session and the buttons, so the highlight and the grade can never disagree. Roles, the accept lists, reason order and the outcome cut (D-08 to D-11) are unchanged.
- **R-09 (planner, owner prefers hidden) Conduct on the ground.** A scenario that offers no conduct (`conduct: none`, which the ground rule demands for ground scenarios, or no `further` section) does not draw the three conduct buttons at all and the session ignores a conduct press; MAYDAY, PAN PAN PAN and BRIEF PASSENGERS are drawn in every run. Documented in GRADING.md and PANEL-REVIEW.
- **R-10 (owner) Graded at Procedure complete.** The selections are evaluated together with the performed panel actions when the user presses Procedure complete; the run does not end earlier and a selection never ends it. Planner details: there is no modal any more, so the run clock no longer pauses for the decisions (choosing costs run time like any action); on Realistic a press before the onset is ignored without any visible difference (buttons are drawn alike, so the onset is not given away).
