## Decisions (assumptions taken in planning; the owner may veto any of them)
Owner decisions D-06 to D-13 of `07-CONTEXT.md` apply, including the multi-select, the Brief passengers wording and the explicit `conduct: none` of the owner's additions of 2026-11-01.
- **F-01 (D-06) The list is aircraft data.** `src/engine/further.ts` defines the types and `defineFurther` (validated like `defineScenes`: ids match `^[a-z][a-z0-9_]*$`, unique, group references exist). A set holds options (`id`, `text`, `kind` action or conduct, optional `group`, optional `debriefNote`), groups (`id`, `text`: only "Inform ATC"), the title of the conduct item ("Choose further flight conduct") and `groundParameter` (the id of the profile parameter that puts the aircraft on the ground). `src/aircraft/da50rg/further.ts` fills it: atc_mayday "MAYDAY (121.5 or current frequency)" and atc_pan_pan "PAN PAN PAN (advise ATC)" in the group atc, brief_passengers "Brief passengers (if time permits)", conduct_continue "Continue flight normally", conduct_precautionary "Initiate precautionary (alternate) landing", conduct_emergency "Initiate emergency landing" with the debrief note "The emergency landing itself is not trained yet." (own wording), groundParameter ground_roll. `AircraftEnv` gets the field `further` (and `DA50RG_ENV` fills it). Nothing outside `src/aircraft` and the scenario files names an option id; `tests/blueprint.test.ts` gets the option ids and the note as forbidden literals for `src/engine`, `src/scenario` and `src/ui`.
- **F-02 (D-08, D-09, D-10) The section.** In `schema.ts` a strict optional `further` with `actions` (a list, default empty, of entries `id`, `role` one of required, recommended, optional, harmful, and `fails_run` boolean default false) and `conduct`, which is required inside the section: either the literal `none` or a strict object with `accept`, a non-empty list of ids. Whether ids exist, `fails_run` on a non-harmful role, ground against accept and the rest are lint (F-05), not schema. Format 1 stays; nothing else in the schema changes.
- **F-03 (D-07) The recording.** `Recording.decisions` is an optional list of `{ t, id }` in the order picked (type `RecordedDecision`). `grade` throws for an id the aircraft does not have, exactly as for an unknown control. Decisions with `t` after the outcome time are not graded (R10 cut). An action id picked more than once counts once (the first). The conduct is graded by the last conduct pick; every pick stays in the result for the debrief.
- **F-04 (D-09, D-11) The result.** `GradeResult.further` is present only when the scenario has the section or the recording has decisions (otherwise the key is absent and the result stays JSON-identical to before). It holds one entry per declared or picked action option in the aircraft's list order (`id`, `role`, `done`, `failsRun`) and a conduct entry (`declared` none or accept, `picks` in order, `last`, `status`: `not_declared`, `ok`, `missing` or `wrong`). New `Reason` kinds in the order of D-11: `further_missed` (count), `conduct` (status missing or wrong), `further_harmful` (id). `debrief-text.ts` gets own-wording lines for them ("N required further actions were missed.", "The flight decision was missing.", "The flight decision was not the right one.", "A harmful further action counts as a fail in this scenario.") and a pure helper that gives the debrief row of a further entry (the label, the role word and the verdict word: Done, Missed, Recommended and not done, Harmful, Right, Wrong, Missing) and the emergency-landing note.
- **F-05 (D-09, D-10) Lint.** L27: every `further.actions` id is an action option of the aircraft and listed once; `fails_run` only on role harmful; a message `file:line:col` at the key. L28: `conduct` is `none` exactly when the profile sets the aircraft's ground parameter above 0 (a ground scenario must say none, any other scenario with the section must say accept); every accept id is a conduct option of the aircraft and listed once; accept must not list all conduct options. The L11 rule stays. L20 (`checkVariantRuns`): the solution recording also carries the required actions and the first accept id of the conduct, so the solution of a variant still passes. Add one `decisions` argument to its recording builder; do not touch the other rules.
- **F-06 (D-07) Session.** `session.decisions` (signal, the log of the run, cleared wherever a run starts or is left), `session.decide(id)` (running only; ignored before the Realistic onset, for an unknown id, for a conduct option when the scenario declares no accept, for an action already logged and for a repeat of the last conduct pick; otherwise appends `{ t: clock.now(), id }`), and `furtherOpen` with `openFurther()` and `closeFurther()` (running only, ignored before the onset). `currentRecording()` (from plan 07-01) adds `decisions` when the log is not empty. The modal holds the run clock like every modal. Available in Training and in Exam mode.
- **F-07 (D-05) The pad.** The FURTHER ACTIONS button (`session.further`, label FURTHER ACTIONS, aria label "Further actions: inform ATC, brief passengers, choose the flight conduct") is drawn in the `further` rectangle of `SESSION_LAYOUT.run` that plan 07-01 reserved, in both modes.
- **F-08 (D-13) Shipped declarations.** The table of D-13 is the content of this plan's third task. The expectations of the shipped files live as a hand-written table in `tests/shipped-further.test.ts`.
- **Owner review points of this plan:** the D-13 table (every role and accept list), the last-pick rule for the conduct, the single-use rule for actions, the pause of the clock while the modal is open, the missing "either call" role (icing).
