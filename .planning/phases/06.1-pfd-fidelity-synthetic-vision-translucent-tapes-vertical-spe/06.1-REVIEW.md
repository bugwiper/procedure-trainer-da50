# Phase 6.1: Code Review Report

**Reviewed:** 2026-11-01
**Depth:** standard
**Files Reviewed:** 12 (plus tests/pfd-layout.test.ts, tests/svt.test.ts, tests/pfd-live.test.ts, e2e/cas-column.spec.ts read as gates)

## Summary

The phase is solid. No crash, security or physics-arithmetic defect was found. Layout is data (`pfd-layout.ts`) with an independent hand-written reference (`tests/pfd-layout-reference.ts`). Physics arithmetic stays within `+ - * /` plus `Math.round` (allowed; the ESLint ban covers only random, exp and pow). The synthetic vision draws no text (G-0). The scene palette is one shared table. No scenario fact leaked into engine or ui.

Points checked and found correct:

- The readout and box clamp at +3000 and -3000, and the box moves symmetrically (`verticalSpeedPointerPx`).
- The readout is the bare magnitude. A negative value shows positive, `-0` gives "0", NaN and Infinity give the base 0, and rounding is symmetric to 50 fpm. All of this is tested in `tests/pfd-live.test.ts`.
- The box travel (y 60.5 to 239.5) stays clear of the CAS column (y >= 287) and inside the content zone (y 30 to 343).
- Synthetic vision `reach` 480 covers the largest zone distance (about 311) plus the pitch shift (132) at every attitude.
- The SVT element count is 43 shapes in the cruise scene (40 field polygons, 2 rects, 1 haze), under the cap of 60.

The "3" at the top of the vertical speed scale looks clipped because of a real defect (WR-01), not because of a clip path.

## Warnings

### WR-01: End numerals "3" straddle the ends of the dark strip and have no backing or halo (the "clipped" look)

**File:** `src/ui/panel/frames/VerticalSpeedScale.tsx:82-92`, `src/aircraft/da50rg/pfd-layout.ts:187-199`
**Issue:** Each numeral is centred on its own tick (`y = yOf(fpm) + numeralSize / 3`). The ±3000 ticks sit exactly on the top (y = 66) and bottom (y = 234) edges of the strip. A size 6 digit (cap height about 4.2) at the top end therefore spans about y 63.9 to 68.1. Its upper half lies outside the 0.55-opacity dark strip, directly on the bright synthetic sky, in grey `#aab3bd`.

There is no clip path. The glyph is unclipped but visually cut in half: the grey digit disappears into the pale sky above the strip edge. The bottom "3" has the same problem against the ground. The other label texts in this frame (KT, FT, HPA, QNH) use `stroke` with `paint-order="stroke"` as a halo, so the numerals are the inconsistent case. The 1000 and 2000 numerals sit well inside the strip and are fine.

No gate catches this. `VS_REF` holds only the numeral count and texts, and no numeral position or bounding box is checked against `VS_STRIP_REF`.

**Fix:** Pick one of the following.

1. Pad the strip beyond the scale ends, for example by half a numeral height plus a margin (about 4 units). The scale stays 84 per half, and the box travel and the reference table update with it:
```ts
export const VS_STRIP_PAD = 4;
export const VS_STRIP = {
  x: 439,
  y: ATTITUDE.cy - VS_HALF_HEIGHT - VS_STRIP_PAD,
  height: 2 * (VS_HALF_HEIGHT + VS_STRIP_PAD),
  // ...
};
```
2. Add the same halo as the unit labels to the numerals: `stroke={TAPE_FILL} stroke-width={2} paint-order="stroke"`.
3. Draw the end numerals just inside the strip, at +3000 minus a half glyph height and -3000 plus one.

In every case, add a gate that each numeral's box lies inside the strip rectangle. Expect to edit `pfd-layout-reference.ts` and `VS_TRAVEL_REF`.

### WR-02: Text fit of the VS readout and numerals is not gated (the CAS column has such a gate)

**File:** `tests/pfd-layout.test.ts:267-325`, `e2e/pfd.spec.ts:14-60`, `src/ui/panel/frames/VerticalSpeedScale.tsx:96-106`
**Issue:** The widest readout is "3000" in B612 Mono at size 7 with `letter-spacing: 0.06em` (from `.panel-svg text`), right-anchored at x 463.5 inside a 22-wide body starting at x 443. My estimate is a left edge near x 445, leaving about 2 units of margin. That is inside the tolerance only if the font loads as expected.

On Linux CI, or with a fallback font while B612 Mono is loading, it can touch or overrun the frame. `e2e/cas-column.spec.ts` measures `getBBox()` against the row width. The VS box has no such measurement, and no test checks the numeral boxes either. Layout is data, but this fit is not a data gate. A font or letter-spacing change would pass every test.

**Fix:** Add an e2e spec (desktop-chromium, with `?q=vertical_speed_fpm:3000`) that checks:
```ts
const box = pointer.locator('path').getBBox();   // body
const txt = pointer.locator('[data-vs-readout]').getBBox();
expect(txt.x).toBeGreaterThanOrEqual(box.x + 1);
expect(txt.x + txt.width).toBeLessThanOrEqual(box.x + box.width - 1);
```
Do the same for each `[data-vs-numeral]` against the strip rectangle (after WR-01).

## Info

### IN-01: Magic number 50 (readout step) and the 3-digit baseline offset are inline, not layout data

**File:** `src/aircraft/da50rg/pfd-layout.ts:243`, `src/ui/panel/frames/VerticalSpeedScale.tsx:87`
**Issue:** `Math.round(magnitude / 50) * 50` and `numeralSize / 3` are literals. The first is the readout resolution and the second is the glyph-centring constant. The reference table has no entry for either. The project convention is that numbers like these are data plus a reference value.
**Fix:** Add `VS_READOUT_STEP_FPM = 50` and `NUMERAL_CENTRE_FACTOR` (or compute the offset in layout data) to `pfd-layout.ts`, with a matching entry in `VS_REF`.

### IN-02: Scenario parameter ranges still ±2000 while the quantity range is now ±3000

**File:** `src/aircraft/da50rg/physics.ts:741,746` versus `src/aircraft/da50rg/quantities.ts:494-500`
**Issue:** `flight_vs_fpm` and `glide_vs_fpm` are capped at ±2000, so no scenario or lag-driven run can reach the outer third of the new scale. The ±3000 clamp, the 2000 to 3000 ticks and the end-of-scale box position are reachable only through `?q=`. This is consistent with the owner decision, but it makes the "scale of the real display" untested in live flows.
**Fix:** Either leave it and note it in the CONTEXT, or widen the two parameter ranges when a scenario needs it.

### IN-03: The element cap does not bite and covers only the SVT shapes

**File:** `tests/svt.test.ts:188-200`
**Issue:** `MAX_SHAPES_PER_SCENE = 60` against an actual 43 (cruise and cloud) leaves 17 shapes of slack. Neither the whole PFD nor the number of nodes redrawn per 100 ms step has a gate. The pfd-layout tests count ticks and numerals but give no frame-level budget.
**Fix:** Tighten the cap to the actual maximum plus a small margin (for example 48), or derive it from a reference table. Optionally add a total-shape budget for the PFD tree.

### IN-04: Duplicate local helpers and constants; geometry still hard-coded in PfdFrame

**File:** `src/ui/panel/frames/VerticalSpeedScale.tsx:19-21,41-44`, `src/ui/panel/frames/PfdFrame.tsx:49-53,65-66,76-79,362-370`
**Issue:**
- `fixed()`, `WHITE`, `TAPE_FILL` and `LABEL` are duplicated in both files.
- `BANK_CY = 150` duplicates `ATTITUDE.cy`.
- The heading text coordinates (x 248, y 302 and 328) and `BANK_R`, `BANK_TICKS` are not in `pfd-layout.ts`, although the file claims to hold the geometry that the gates read.

**Fix:** Move the shared colours and `fixed` to a small `frames/glass-style.ts` or into `MfdFrame.tsx`. Use `ATTITUDE.cy` for `BANK_CY`. Move the bank scale and heading text anchors into `pfd-layout.ts` with a reference entry.

### IN-05: Garbled over-long comment in quantities.ts; fixed gradient ids in SyntheticVision

**File:** `src/aircraft/da50rg/quantities.ts:10-14`, `src/ui/panel/frames/SyntheticVision.tsx:222-247`
**Issue:**
- The header comment was patched by splicing the `qnh_hpa` sentence into the middle of an existing line. It is a single very long line that reads "...no model moves them (the de-ice quantity has a rate model...), a scenario may set them". It is hard to read, and Prettier does not reflow comments.
- The SVT gradients use the fixed ids `pfd-svt-sky`, `pfd-svt-ground`, `pfd-svt-haze` and `pfd-svt-runway`, and the attitude clip uses the existing `pfd-attitude-clip`. If a second PFD instance (a zoom clone or preview) were ever mounted, the duplicate ids would resolve to the first definition. This is harmless today because there is exactly one PFD.

**Fix:** Rewrap the comment as two sentences. Optionally prefix the ids with the region id (`${region.id}-svt-sky`) if a second PFD instance is ever planned.
