## Decisions (planner choices; the owner may veto any of them)
The owner's findings of the walkthrough of the emergency landing (2026-11-03) are in `09-CONTEXT.md` as R-10 to R-17 and are binding. R-13 supersedes the conduct condition of D-02, D-03 and R-04; R-14 supersedes the no-carry clauses of D-02 and R-07 and the matching deferred idea. Three tasks on purpose: the tracer is the follow-on path from the debrief to a started, carried run (the riskiest change, every layer from the engine to the page), then the content changes that depend on the new rules, then documents and the final gates.
- **P-01 End state of 09-04 and where it may differ.** This plan is written against the tree as 09-04 leaves it. At the time of writing 09-04 had committed its task 1 (`8508870`: list-form `follow_on` with weights, `followOnFromSeed`, `Recording.followOn`, `offersRealistic`, the debrief note reworded) and was executing task 2 (the ditching, uncommitted). Everything in this plan about the ditching, the second target of the fire sources and the PANEL-REVIEW items 18 and later is read from 09-04's plan, not from code. Before the first edit run `git log --oneline -8`, `git status --short`, read `scenarios/landing/ditching.toon`, the two fire sources, `e2e/landing.spec.ts`, `e2e/follow-on.spec.ts`, `e2e/support/session.ts` and the Phase 9 section of `docs/PANEL-REVIEW.md` (grep, then read the range) and adapt names, file order and item numbers where they differ, keeping the intent, and say so in the SUMMARY. Known soft points: the situation text of the ditching (09-04 wrote "with the gear extended"), the helper names of the e2e support file, the item numbers of PANEL-REVIEW, the lines 09-04 wrote into ROADMAP.md (its task 3 sets "Plans: 4 plans" and the progress row 4/4: this plan changes them to 5 plans and 5/5).
- **P-02 The offer rule, no schema change.** `further.follow_on` keeps the shape 09-04 gave it (a map from a conduct option id to a list of one to four targets with weights). The key still names the aircraft's button texts and keeps L33 coherent (the scenario accepts that conduct); it no longer decides when the buttons show. The offer takes the targets of every key in file order. Alternative rejected: a flat list without a key, because it would change the schema, L33, L34, the aircraft table, README and about twenty tests that 09-04 has just written, for no gain the owner asked for.
- **P-03 Confirm step.** One optional step key `confirm: true`. Grading is untouched (rules 5 and 6 already enter a step that holds at the start at the start and credit it while it holds after the last action); only authoring changes: L5 does not report it, a new L35 reports a confirm step that is false at the start and one in a scenario with an onset (R12), L11 does not count it. The sheet and the debrief show it Done from the first frame because the panel shows it. Alternative rejected: a plain line (the row could no longer be violated). Lint rule numbering continues after L34; the next free number is L35.
- **P-04 Carry shape and capture.** `Recording.carry` is the full record of every control id to its state as the source run left it (about 100 short entries), not a difference: a difference against the registry defaults would let the follow-on file's own start controls win for every control the pilot left at its default (the emergency fuel pump of the engine-off landing would come back on although the pilot had left it off). It is captured by one pure function `carryOf(registry, state)` when the run completes (all four ends), kept in a closure variable of the session, handed to the follow-on start and cleared with the panel. A momentary button is captured at its rest state: a held press cannot be carried.
- **P-05 Precedence (R-14 d).** Controls come from the carry for every control; quantities come from the file; the simulation then moves control-derived quantities to the targets the models give for the carried controls within their own time constants (seconds), exactly as after a switch moved by the pilot; nothing is back-computed and no settling step is added before the first frame (it would change the replay start). `engine_stopped` of the profile keeps winning for the physics over a carried engine master or fuel valve. The one start quantity that depends on a control in the shipped landing, `fuel_trans_active`, leaves the file with the pump change, so no shipped file sets a start value that a carry can contradict except the dead-engine values, which hold under `engine_stopped` whatever the switches say; one test proves it with a carried engine master ON.
- **P-06 Doors and windows are a sweep with a table, not a guess.** The finding is established from the shipped files: ten rows name a door or the emergency window, eight are already steps (the table in R-12 and in `tests/shipped-doors.test.ts`), two (ENGINE FIRE rows 7 and 8) are plain lines and become optional steps. Severity optional in flight is owner decision S-07 and stays; the two rows are credited whenever the window or door opens because the simulation has no standstill.
- **P-08 The two-line choose tabs (R-17), placed in task 3.** It is a small, independent label change, so it rides with the documents and gates and not with the tracer. The tab text is the `tab` of the catalog group (aircraft data) with a line feed, drawn by the existing line-feed mechanism of `SessionButton`; that component has one fixed label size (14) and one fixed line step (18), so it gets an optional label size and a line step that scales with it. "Non-annunciated" is 15 characters: by the panel's glyph rule (0.62 of the size per character, as `tests/further-pad.test.ts` uses) it needs a size of about 11 to stay inside a 116.67 unit tab with a margin, so the size is chosen from the sizes already in use on the panel by the fit gates, not by eye. Verified by grep before planning: no e2e helper selects a tab by its text (the shared `pressChooseTab` uses the group id), so only the specs that read the label itself change.
- **P-07 Existing specs that assumed no carry.** The landing and follow-on e2e flows that go through the debrief button start with the panel the fire run left, so a helper that toggles a control to the printed state would turn it back. Those helpers become state-aware (act only where the control is not yet in the printed state); the flows that choose the landing from the chooser keep the full preparation. The spec that says a run without the emergency landing shows no button flips (R-13); ELEC FIRE FLIGHT, which declares no follow-on, still shows none. Nothing is loosened or skipped; every changed expectation is listed in the SUMMARY.
