# Phase 01.1 (with 01.2 changes): Code Review Report

**Reviewed:** 2026-10-21T22:30:00Z
**Depth:** standard
**Files Reviewed:** 57
**Status:** issues_found

## Summary

Scope was every `src/` file changed since `7268ede` (phases 01.1 and 01.2). Reading depth was uneven by design. The gesture core (`press-arbiter.ts`, `zoom.ts`, `tap-intent.ts`, `press-targets.ts`), the engine (`store.ts`, `registry.ts`, `indicators.ts`, `rotary.ts`, `detents.ts`), `bridge.ts`, `App.tsx`, `stage.css`, `Panel.tsx`, `PanelShell.tsx`, all widgets, the breaker and `PushButton` (first 120 lines) skins, the glass and unit frames, `avionics.ts`, `bus-boxes.ts`, `panel.ts`, `indicators.ts` and the pedestal, engine, gear, de-ice and breaker data files were read in full or in the relevant part. `Bat`, `Rocker`, `Flap`, the later part of `LeverHandles`, `PfdFrame`, `StandbyEfisFrame`, `placards.ts`, `plates.ts` and the remaining control data files (`buttons`, `knobs`, `lights`, `mfd`, `switch-bank`, `under-panel`) were only skimmed or checked through data probes.

Probes run with a throwaway Vitest config kept outside the repo. Together they showed that the layout data holds its invariants today: no region overlaps, no control hit leaves its region, no hit rectangles overlap, every placard and plate reference resolves, and every indicator can be both lit and unlit. This also means the registry gaps in WR-04 are latent, not live.

What I examined and found sound:
- **Press arbiter.** The state machine has no stuck-pending path. Every exit (up, cancel, stale sweep, pinch takeover, reset) emits `pending off`, `discard` or `release`. Stale records with a reused pointer id are routed to the stale record, not the fresh one (`zoom.ts` `apply`, lines 248-253).
- **Hold timer.** It is a single timer, cleared on every event and on detach. Its deadline is taken from the event clock, and `tick` is called with the deadline itself. Racing the timer against `pointerup` produces the same net event pair either way.
- **Capture bookkeeping.** `captured` and `records` are always cleaned when the machine drops a pointer.
- **SVG element count.** It is bounded by static data and guarded by `e2e/breaker.spec.ts`.
- **Text paint.** No `paint-order` and no stroked text exists in `src/`. The WebKit stroked-title problem was already designed out (`bus-boxes.ts` line 72).
- **Production build.** `window.__panel` is stripped from `dist/` and present only in `dist-e2e/`.

The one correctness defect that changes graded behaviour is CR-01. The widgets that own their pointer bypass the single place that rejects non-left mouse buttons. The remaining findings are hardening gaps, a pinch discontinuity, an a11y gap and a stacking defect.

## Critical Issues

### CR-01: Right and middle mouse buttons actuate knobs and drag levers, and own-class widgets ignore the arbiter

**File:** `src/ui/panel/widgets/Rotary.tsx:286-337`, `src/ui/panel/widgets/DetentLever.tsx:497-538`, contrast `src/ui/panel/zoom.ts:375`
**Issue:** `zoom.ts` `onDown` drops every mouse `pointerdown` whose `button !== 0` before the arbiter sees it. The two widgets that keep their own pointer (the rotary body and the drag-lever handle) are `own` targets. They run their own JSX `onPointerDown` / `onPointerUp` and check only `e.isPrimary`, which is always true for a mouse. A right-click or middle-click on a knob therefore starts a widget gesture, captures the pointer, and on release runs the tap path: `stepStop(...)` or `tapStop(...)` followed by `bridge.actuate(...)`. A right-click-drag on a lever handle commits a detent in the same way. The result is a real event in the action log, which is the grading record, caused by a click the arbiter explicitly rejects. The contextmenu opens at the same time. No test covers non-primary buttons (grep of `e2e/` and `tests/` for `button: 'right'` and `contextmenu` finds nothing).

The same root cause is wider than mouse buttons. The widgets gate only on `isPrimary` and never ask the arbiter whether it accepted the pointer. The arbiter marks a pointer `ignored` when another pointer already owns or holds a press. A primary pen pointer landing on a knob while a touch pointer holds a momentary button is `ignored` by the arbiter, yet `Rotary` still begins a gesture and later actuates.

**Fix:** Make the gesture layer the single gate. In `zoom.ts` `onDown`, stop the event from reaching widget handlers when it is not accepted:
```ts
const onDown = (e: PointerEvent) => {
  if (e.pointerType === 'mouse' && e.button !== 0) {
    e.stopPropagation(); // capture phase on the svg: widgets never see it
    return;
  }
  // ... existing code, then after arbiter.down(...):
  if (arbiter.stateOf(e.pointerId) === 'ignored') e.stopPropagation();
```
The widgets then only ever see pointers the arbiter accepted (`pending` or `owned`). As defence in depth, also add `if (e.pointerType === 'mouse' && e.button !== 0) return;` to `Rotary.onPointerDown` and `DragLever.onHandleDown`. Add an e2e or unit case: right-click on `sw.fan` and on a lever handle records no event.

## Warnings

### WR-01: A throwing store listener leaves state and log updated but skips later listeners and the return value

**File:** `src/engine/store.ts:88-92` and `:122-125`
**Issue:** `dispatch` mutates `state` and pushes onto `log` before it notifies, then calls listeners in a bare `for` loop. If one listener throws, the event is already committed, the remaining listeners are skipped, and the exception replaces the `{ ok: true, event }` result. Verified with a probe: a first listener that throws leaves `lv.gear` at `down` with one logged event, the second listener is never called, and `dispatch` throws. `bridge.ts` subscribes first, so today the signals update. Phase 3 will add engine listeners after it, and one failure then leaves the store, the signals and the reaction engine disagreeing. `retract` has the same shape: `this.log.length = seq` and the new state are applied before the retract listeners run, so a throwing listener leaves the log shortened while the caller sees an exception and cannot tell whether the retract happened. The caller in `tap-intent.ts` then reads that as a refused retract and actuates the second tap, which can double-apply.
**Fix:** Isolate each listener and report afterwards:
```ts
const errors: unknown[] = [];
for (const listener of [...this.listeners]) {
  try { listener(event); } catch (e) { errors.push(e); }
}
if (errors.length > 0) queueMicrotask(() => { throw new AggregateError(errors); });
return { ok: true, event };
```
Apply the same pattern in `retract`.

### WR-02: `retract` addresses an event by log position, and the next event reuses that position

**File:** `src/engine/store.ts:108-126`, `src/ui/panel/tap-intent.ts:152-153`
**Issue:** A `seq` is an index into the current log, and the docs say outright that "the next accepted event reuses the retracted seq". The double-tap tracker keeps `last.seq` and later calls `retract(first)`. That is safe today only because nothing else shrinks the log and every other event path calls `pairBreak`/`reset`. It is a discipline invariant, not an enforced one. A stale `seq` held by any consumer (the tracker today, a Phase 3 reaction or a replay log tomorrow) silently names a different event once the position is reused. `markConsumed` is seq-based too, so a consumed watermark can protect the wrong event after a retract and re-dispatch.
**Fix:** Give events a monotonically increasing unique id (a counter that is never reused) and keep `seq` as a position only for display. Retract and `markConsumed` then take the id. Alternatively make `retract(event: ControlEvent)` compare object identity against `this.log.at(-1)`.

### WR-03: Pinch on a region-zoomed view narrower than 200 units jumps to 200 wide, so a pinch-in zooms out

**File:** `src/ui/panel/viewport.ts:11` and `:55`
**Issue:** `pinchRect` clamps `width = Math.min(Math.max(wanted, MIN_VIEW_WIDTH), viewBox.w)` with `MIN_VIEW_WIDTH = 200`. `zoomRect` (double-tap region zoom) produces views narrower than that for 16 of the regions: `deice` 195, `deice_switches` 195, `engine_controls` 190, `light_knobs` 170, both `pfd_bezel_*` 88, `audio_panel` 80, `standby_efis` 140, `autopilot_panel` 106, `mfd_bezel_right` 104, `level` 68, `right_panel` 140, `cb_strip` 138 and the three `under_panel_*` 100 to 110. Verified with a probe: a 1 percent pinch-in on the `level` view returns `w = 200`, and likewise for every region listed. The first pinch move on any of these views therefore snaps the view wider (a zoom out of up to about 3x on `level`), and pinch-in can never go below 200. This is visible as a jump on phones, the device class the zoom exists for.
**Fix:** Clamp the minimum to the current width when it is already below the floor, so that pinch never widens the view while the fingers move apart:
```ts
const floor = Math.min(MIN_VIEW_WIDTH, current.w);
const width = Math.min(Math.max(wanted, floor), viewBox.w);
```
Add a `zoom.test.ts` case for each region narrower than `MIN_VIEW_WIDTH`.

### WR-04: `defineRegistry` does not validate several fields the widgets and the viewport depend on

**File:** `src/engine/registry.ts:600-637` (and the `check*` helpers above it)
**Issue:** Validation is thorough for ids, states and skins, but these gaps remain:
- `x`, `y` and `hit` are validated only for rotaries (radius fit) and circuit breakers (positive hit). A toggle, lever, button or guarded toggle with `hit.w <= 0`, `NaN` or `Infinity` passes.
- `GuardedToggleDef.guardOpenHit` is never checked (finite, positive sides, inside the region). `controlFootprints` and `targetSide` read it.
- `DetentLeverDef.track.length` (positive, finite) and `track.axis` are unchecked. `LeverBody` computes `side = Math.min(across, along - length, spacing)` for the marker and handle rectangles. If the hit along the track is not longer than the track, `side <= 0` produces SVG rects with negative width or height, which are silently not drawn and not tappable.
- `ControlBase.hit` is documented as "every interactive sub-target of the control lies inside it", and a control centre plus hit should lie inside its region. Neither is enforced. `defineIndicators` does check that a lamp disc lies inside its region, so the two registries are inconsistent.
- Region `bounds` are never checked (positive, inside `viewBox`).
- `Object.freeze({ ...spec })` is shallow: `states`, `detents` and `stops` arrays stay mutable and shared with the module constants.

The current data satisfies all of these (verified by a probe over the 93 controls and all regions), so this is a latent risk for the planned YAML aircraft and pack data, which the project says non-developers will author.
**Fix:** Add a `checkGeometry(def, region)` pass in `defineRegistry`. Require finite `x`, `y`, `hit.w`, `hit.h`, positive hit sides, the footprint inside `region.bounds`, `guardOpenHit` finite, positive and inside the region, and `track.length > 0` with `along - length > 0` for non-tap-toggle levers. Validate region bounds against `viewBox`, and deep-freeze the arrays.

### WR-05: The panel is pointer-only, and operable controls are exposed as `role="img"`

**File:** `src/ui/panel/widgets/Toggle.tsx:126`, `CircuitBreaker.tsx:67`, `MomentaryButton.tsx:94`, `Rotary.tsx:356`, `DetentLever.tsx:284` and `:171`, `GuardedToggle.tsx:112` and `:137`, `src/ui/panel/Panel.tsx:57-63`
**Issue:** Every control is a `<g role="img" aria-label=...>` with a transparent `<rect>` hit target and pointer handlers only. None is focusable (`tabindex`), none handles keyboard events, and the role announces a picture, not a switch, button or slider, so assistive technology neither exposes the state change as an operable control nor offers a way to operate it. The root `<svg>` carries `aria-label` without a `role`, which several screen readers ignore. The only keyboard-reachable elements in the app are the footer buttons, the rotate hint and the Full panel button. The project brief lists desktop use and an accessibility guardrail (axe is in the stack), so a keyboard path is a stated quality target. It need not be v1-blocking, but the `role="img"` labelling is actively misleading.
**Fix:** At minimum, give controls a correct role (`switch` with `aria-checked` for two-state toggles, `button` for momentary and breaker, `slider` with `aria-valuetext` for levers and knobs) plus `tabindex="0"` and Enter/Space handling that calls the same `press`/`tap` target methods the gesture layer calls. Set `role="group"` or `role="application"` on the root svg. If the keyboard path is deferred, record it as a known gap in the phase notes.

### WR-06: The Full panel button paints above the About overlay, which also lacks focus containment

**File:** `src/ui/stage.css:103-111` (`.about`, `z-index: 20`) vs `:151-158` (`.zoom-out`, `z-index: 30`), `src/ui/App.tsx:80`, `src/ui/about/About.tsx:20-27`
**Issue:** `.about` is `position: fixed; z-index: 20` and is rendered as a child of `.stage` (which is `position: fixed`, so it is the stacking context). `.zoom-out` sits inside `.panel-area` (`position: relative`, no `z-index`, so no stacking context of its own) at `z-index: 30` in the same context. While the view is zoomed and About is open, the Full panel button therefore draws above the opaque overlay and stays clickable. The dialog sets `aria-modal="true"` but does not trap focus or mark the background inert, so Tab walks back into the panel behind it. Closing it does not return focus to the "About and content policy" opener.
**Fix:** Give `.about` a higher z-index than every other overlay (for example `z-index: 40`), or hide `.zoom-out` while `aboutOpen`. Set `inert` on `.panel-area` and the footer while the dialog is open (or implement a focus trap), and restore focus to `about-open` on close.

### WR-07: The graded action log hands out its own mutable event objects

**File:** `src/engine/store.ts:67-69` and `:89-91`
**Issue:** `events()` returns `this.log.slice()`, which copies the array but not the objects. `dispatch` returns, and passes to every listener, the same object that sits in the log. `ControlEvent` is `readonly` only at compile time. Any listener, the `bridge`, or Phase 3 code that mutates `event.t` or `event.value` rewrites the grading record, and `deriveState` replays whatever the objects now say. The documented guarantee is "the log stays the truthful grading record".
**Fix:** `const event: ControlEvent = Object.freeze({ seq, t, id, value, source: 'user' });` and `events()` can then keep returning `slice()`.

## Info

### IN-01: Event times are dispatch-time `performance.now()`, and a quick momentary tap logs press and release at the lift

**File:** `src/ui/bridge.ts:102-104`, `src/ui/panel/press-arbiter.ts:386-390`, `src/ui/panel/zoom.ts:260-266`
**Issue:** `actuate` stamps `performance.now()` at dispatch, not the pointer event time. A committed hold logs `press` about 100 ms after the physical down (at the commit). A lift inside the 100 ms hold window logs `press` and `release` back to back at the lift time. Grading a hold duration (the GEAR TEST lamp test, the MAX run) will read short taps as about 0 ms and long holds as 100 ms short.
**Fix:** Pass the event's `timeStamp` through the press target (`PressInfo.downAt` and `upAt`) to `actuate`, so the log carries physical times. Decide this before Phase 3 consumes durations.

### IN-02: Zoom state is module-level singleton state, and `buttonCorner` is an impure computed

**File:** `src/ui/panel/zoom.ts:30-64`, `:139-141`
**Issue:** `viewRect`, `fullView`, `footprints`, `lastCorner` and `tapViewChangeAt` live at module level. `attachZoomGestures` rewrites `fullView`, `footprints` and `lastCorner` but not `viewRect` or `tapViewChangeAt`, and its cleanup resets none of them. A re-run of the `Panel` effect (changed `registry` or `bridge` dependency, HMR) leaves a stale zoomed view and a stale stray-click timestamp. `buttonCorner` is a `computed` that assigns `lastCorner` and reads it back non-reactively, so its result depends on call history, and resetting `lastCorner = 'tr'` at attach does not invalidate the cached value.
**Fix:** Reset `viewRect`, `tapViewChangeAt` and `lastCorner` in the cleanup, or create the view state per attach. Keep the corner memory in a signal, or pass the previous corner into the computation explicitly.

### IN-03: Placards and the temperature triangle drop silently on an unresolved reference

**File:** `src/ui/panel/PanelShell.tsx:393-399` and `:264-281`
**Issue:** `Placards` returns `[]` when `registry.get(placard.near)` or its region is missing, and `temperatureTriangle` returns `undefined`. A renamed control id removes its engraved text from the panel with no error. The current data resolves (checked), so this is a loud-failure gap, not a live bug.
**Fix:** Throw (or log in dev) in these branches, or validate `PLACARDS[].near` against the registry in a unit test and in `defineRegistry`'s caller.

### IN-04: The `?regions=1` developer overlay ships in the production bundle

**File:** `src/ui/panel/Panel.tsx:39-40`, `:82-98`
**Issue:** Any visitor can add `?regions=1` to draw region frames and captions. Harmless, but it is the only test or dev switch left in the production build (`__panel` is correctly stripped).
**Fix:** Gate it on `import.meta.env.DEV` or `VITE_TEST_HOOKS`.

### IN-05: Touch targets below the project's 44 px guidance in the app chrome

**File:** `src/ui/stage.css:85-100` (`.footer-link`, `min-height: 28px`), `:217-223` (`.rotate-hint button`, `min-height: 28px`)
**Issue:** The footer link and the rotate-hint dismiss button, both used on phones, are 28 px high, while the Full panel button and the About close button are 44 px. The panel controls are held to 44 px by tests.
**Fix:** Raise both to `min-height: 44px` (the footer is allowed to wrap).

### IN-06: Geometry rules are duplicated by hand between widgets and the viewport model, and key formats are coupled by string

**File:** `src/ui/panel/viewport.ts:100-148` vs `src/ui/panel/widgets/DetentLever.tsx:220-229`; `placardLines` / `splitAtSpace` in `DetentLever.tsx:27-35`, `Rotary.tsx:43-51`, `skins/PushButton.tsx:50-60`; `DetentLever.tsx:132` vs `:373`
**Issue:** `targetSide` re-implements `LeverBody`'s `side = min(across, along - length, spacing)` computation, and the comment says it "mirrors the widgets", so a change in one silently breaks the 44 px guarantee tests only if the tests compare them. Three near-identical "split a label at the space nearest the middle" helpers exist. The join key `` `${def.id}:${state}` `` built in `makeHandlePress` must equal the marker's `data-detent` value `` `${def.id}:${d.id}` `` built in `LeverBody`, and nothing links the two formats.
**Fix:** Export the lever hit-side computation from one module and use it in both places, share one label-splitting helper, and add `markerKey(def, detent)` used by both key builders.

### IN-07: Gauge components divide by `max - min` without a guard

**File:** `src/ui/panel/frames/ArcGauge.tsx:27`, `src/ui/panel/frames/BarGauge.tsx:21`
**Issue:** `(clamped - min) / (max - min)` is `NaN` or `Infinity` if a gauge is ever given `max === min`, and the resulting `NaN` lands in `d`, `x` and `transform` attributes. Today every `GaugeSpec` is static and valid. The shared `key` for bands is `${from}-${to}`, which would duplicate for two identical bands. Both matter once live values (PNL-04) and data-driven specs arrive.
**Fix:** `if (!(max > min)) throw new RangeError(...)` in a shared `scaleFraction` helper, and `if (!Number.isFinite(value))` fall back to `min`.
